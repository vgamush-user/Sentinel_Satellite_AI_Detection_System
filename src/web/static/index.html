Field guide

From telemetry to review

Both workflows use simulated CubeSat telemetry. They differ in when analysis starts and what evidence they return.

Comparison of SentinelSat workflows
StageWeb workspaceAnalysis demo
InputReplay or injected test rowsLatest replay window at submission
TriggerIncident guards for confidence and row countStatistical screening, then full analysis on request
OutputScored rows, incident evidence, and report when availablePrediction, SPARTA context, policy outcome, and narrative when returned

Hosted demo · Five-stage analysis

  1. MonitorStatistical screening against the nominal baseline.
  2. ClassifierXGBoost predicts a class. The agent presents the model output.
  3. SPARTA AnalystMaps the predicted class to threat context. The mapping does not establish attribution.
  4. MitigationA deterministic policy selects an action from the class and score.
  5. Incident ReporterSummarizes the evidence and review context.

The statistical Monitor checks the replayed window. A manual analysis can proceed after a Monitor decline.

Web workspace · Kafka telemetry replay

The detector scores replay and test rows. The incident manager groups qualifying rows using the configured confidence and row-count guards. Reports may be generated for the incident sample or drawn from a cached example.

Reported model evaluation

68.9% Domain-shift accuracy

0.697 Macro F1

Project report figures for training on clean simulated telemetry and evaluating on noised telemetry. The near-perfect clean in-domain result is a simulator ceiling and an unsuitable estimate of generalization. Replay session accuracy uses a different denominator.

Why review matters

The reported experiment counted 1,786 Normal windows predicted as Data Injection. A blended Command Flooding and Data Injection case produced a 0.999 confidence score for Data Injection despite ambiguous evidence.

Per-window feature attribution is unavailable in this build. The demo uses simulated telemetry and reports policy outputs for review.
